## 背景
大前提として本アプリケーションは、現職の職務履歴兼、過去案件の設計の振り返り、PoCとしてのサンドボックスとして
運用をすることを考慮し、技術スタックを選定しております。
  

そのため、基本的にプログラミング言語やフレームワークのバージョン、デプロイの環境は可能な限り、準拠しております。
  
   
一方で、コストや環境のアクセスパターンから一部データベースやネットワークなどのAWSのインフラ構成を個人開発向けにチューニングしています。


## 使用技術

- Java 17
- SpringBoot 3.5.9
- Spring Security 6.5系
- Gradle 8.10.2
- Docker
- AWS

## バックエンド関連 AWS サービス

### ネットワーク

| サービス             | 用途                                         | 備考                                   |
| -------------------- | -------------------------------------------- | -------------------------------------- |
| VPC                  | バックエンドのネットワーク基盤               | Public Subnet × 2 AZ構成、NAT GW不使用 |
| VPC Link             | API GatewayからVPC内ECSへの接続              | 専用Security Group付与                 |
| VPC Gateway Endpoint | VPC内からDynamoDB/S3へのプライベートアクセス | 無料                                   |

- 理想的ではないが、コスト削減やアクセスの頻度を考慮し、パブリックサブネットに配置
  - VPCエンドポイントの場合: ECR(dkr,api), CloudWatch, SSMの分のエンドポイント料金がかかる
  - NAT Gatewayの場合：そのままつけていると$32/月かかる
  - NATインスタンスの場合：Getewayよりマシだが、起動・停止などの運用負荷がかかる
  - Security Groupの設定で、VPC Linkからのインバウンドのみ許可することである程度は防止可能

### API管理 / CDN

| サービス               | 用途                            | 備考                 |
| ---------------------- | ------------------------------- | -------------------- |
| API Gateway (HTTP API) | APIルーティング・スロットリング | 従量課金、ALB代替    |
| CloudFront             | HTTPS終端・CDN配信・API振り分け | /api/* → API Gateway |

- タスク1台構成でロードバランシング不要なためALBを不採用、固定費（約$16〜22/月）を削減
- REST APIを使用したかったが、REST APIのVPC統合にはNLB/ALBを仲介させる必要があるため、HTTP APIを使用
- CloudFrontで静的ファイル配信とAPI振り分けを一元化し、HTTPS終端を担当

### コンピューティング

| サービス     | 用途                                          | 備考                                  |
| ------------ | --------------------------------------------- | ------------------------------------- |
| ECS Fargate  | SpringBootアプリケーション実行                | 3サービス (users / products / orders) |
| Fargate Spot | コスト削減のためのキャパシティプロバイダ      | 最大70%コスト削減                     |
| Cloud Map    | ECSタスクのDNS自動登録 (サービスディスカバリ) | namespace: ecapp.local                |

- あまりサーバー管理を意識したくない、タスク定義回りやECSの設定回りは現職でもちょくちょく遭遇するためFargateを採用
- コスト削減・ポートフォリオ用途から中断リスクを許容できるため※、Fargate Spotを採用
- Cloud Map：ECSタスクのIP変動を吸収するサービスディスカバリ。追加コストもないため採用

※ 許容できないのであれば、サーバーを増やす、ロードバランサーを設けるなどしたほうが早いので…

### データ / ストレージ

| サービス            | 用途                       | 備考                           |
| ------------------- | -------------------------- | ------------------------------ |
| DynamoDB            | データ永続化               |                                |
| S3 (商品画像)       | 商品画像保存               | ecapp-product-images-{account} |
| S3 (フロントエンド) | フロントエンドホスティング | ecapp-frontend-{account}       |

- コスト削減、兼、現職のアーキテクチャを管理する中である程度アクセスパターンが検討でき、RDBを使う方が過剰に見えるためKVSを採用
  - 商品詳細などパスにキーがあるページ：基本PKで引くことが可能
  - 検索画面系：検索エンジン系からPKを取得し、その後補完するための情報取得はPKを使用してKVSから取得
  - 管理画面系：GSIなどで店舗のIdを組み合わせて返す
