    1. プロジェクト構成

    1.1 マルチモジュール構成

    モジュール 役割
    common 全サービス共通のConfig・例外・定数・ユーティリティ
    dynamodb (schale) DynamoDBアクセス層（Entity・Repository）
    products 商品に関連するAPIはここで実装する
    orders 受注に関連するAPIはここで実装する
    users ユーザーや店舗に関連するAPIはここで実装する

    1.2 パッケージ構成（各APIモジュール）

    com.project.abydos.saki.api.{モジュール名}/
├── constant/       # エンドポイントパス、ログメッセージ等の定数
├── controller/     # REST Controller
├── facade/         # ビジネスロジックの集約・レスポンス変換
├── request/        # リクエストDTO
├── response/       # レスポンスDTO
├── service/        # ドメインロジック・DB操作
└── exception/      # モジュール固有の例外（必要な場合のみ）

    2. レイヤー責務

    レイヤー 責務 禁止事項
    Controller リクエスト受付・バリデーション指示・Facadeへの委譲 ビジネスロジックを書かない
    Facade サービス呼び出しの集約・レスポンスDTO変換 Repositoryを直接呼ばない
    Service ビジネスロジック・Repository呼び出し レスポンスDTOを返さない
    Repository データアクセスのみ ビジネスロジックを持たない

    2.1 Controller - 禁止: ビジネスロジックを書かない

    // ✗ NG: Controllerにビジネスロジックが入っている
@GetMapping("/orders")
public ResponseEntity<OrdersApiResponse> getOrders(@Valid OrdersApiRequest request) {
    Long userId = SecurityUtils.getCurrentUserId();
    List<Order> orders = orderRepository.findByUserId(userId);
    // ここでマッピングや計算をすべきでない
    long total = orders.stream().mapToLong(Order::getTotal).sum();
    return ResponseEntity.ok(new OrdersApiResponse(orders, total));
}

// ✓ OK: Facadeに委譲するだけ
@GetMapping("/orders")
public ResponseEntity<OrdersApiResponse> getOrders(@Valid OrdersApiRequest request) {
    return ResponseEntity.ok(ordersFacade.getOrders(request));
}

    2.2 Facade - 禁止: Repositoryを直接呼ばない

    // ✗ NG: FacadeがRepositoryを直接使っている
@Component
@RequiredArgsConstructor
public class ProductFacade {
    private final ProductRepository productRepository; // NG

    public ProductResponse getProduct(Long productId) {
        Product p = productRepository.findById(productId)
                .orElseThrow(DataNotFoundException::new);
        return ProductResponse.builder().productId(p.getProductId()).build();
    }
}

// ✓ OK: Serviceを経由する
@Component
@RequiredArgsConstructor
public class ProductFacade {
    private final ProductService productService;

    public ProductResponse getProduct(Long productId) {
        Product p = productService.getProductById(productId)
                .orElseThrow(DataNotFoundException::new);
        return ProductResponse.builder().productId(p.getProductId()).build();
    }
}

    2.3 Service - 禁止: レスポンスDTOを返さない

    // ✗ NG: ServiceがレスポンスDTOを生成している
@Service
@RequiredArgsConstructor
public class ProductService {
    private final ProductRepository productRepository;

    public ProductResponse getProduct(Long productId) { // NG: Response型を返している
        Product p = productRepository.findById(productId).orElseThrow();
        return ProductResponse.builder().productId(p.getProductId()).build();
    }
}

// ✓ OK: Entityまたはドメインオブジェクトを返す（DTO変換はFacadeの責務）
@Service
@RequiredArgsConstructor
public class ProductService {
    private final ProductRepository productRepository;

    public Optional<Product> getProductById(Long productId) {
        return productRepository.findById(productId);
    }
}

    2.4 Repository - 禁止: ビジネスロジックを持たない

    // ✗ NG: Repositoryで在庫チェック等のビジネス判定をしている
public Product findAvailableProduct(Long productId) {
    Product p = table().getItem(Key.builder().partitionValue(productId).build());
    if (p == null || !"O".equals(p.getStatus())) { // NG: 販売中判定はServiceの責務
        throw new ProductUnavailableException("...");
    }
    return p;
}

// ✓ OK: データ取得のみ
public Optional<Product> findById(Long productId) {
    return Optional.ofNullable(
        table().getItem(Key.builder().partitionValue(productId).build())
    );
}

    3. 命名規約

    3.1 クラス名

    種類 命名パターン 例
    Controller {リソース名}Controller ProductController
    Facade {リソース名}Facade ProductFacade
    Service {リソース名}Service ProductService
    Repository {テーブル名}Repository OrderRepository
    Request DTO {API名}Request LoginRequest
    Response DTO {API名}Response ProductResponse
    Entity テーブル名の単数形 Product, Order
    例外クラス {内容}Exception DataNotFoundException
    エラーコードEnum {スコープ}ErrorCode ErrorCode, OrderErrorCode
    ログメッセージEnum {スコープ}ErrorLogMessage CommonErrorLogMessage
    定数クラス 用途に応じた名詞 Endpoint, SecurityConstant

    3.2 フィールド・変数

    • Java標準のcamelCaseを使用する
    • JSONプロパティはsnake_caseとし、@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class) で変換する
    • DynamoDBカラム名はsnake_caseとし、@DynamoDbAttribute で明示する

    3.3 エンドポイントパス

    • snake_caseを使用する（例: /api/v1/products/{product_id}）
    • パス定数はEndpointクラスまたは各モジュールのEndpointクラスで管理する

    4. 共通ライブラリ利用方針

    4.1 Lombok

    • @RequiredArgsConstructor でコンストラクタインジェクションを行う（@Autowiredは使用しない）
    • @NonNull をメソッド引数のnullチェックに使用する
    • @Slf4j でロガーを宣言する

    4.2 Spring Boot

    • バリデーションは jakarta.validation アノテーションを使用する
    • Controllerの引数には @Valid を付与する
    • プロファイルは local / dev で切り替える

    5. 例外処理

    5.1 共通例外

    例外 用途
    ApiException 共通ビジネスエラー（ErrorCodeを指定してスロー）
    DataNotFoundException 対象データが存在しない場合

    5.2 モジュール固有例外

    • ordersモジュールのように固有エラーが必要な場合のみ、パッケージ内に専用ExceptionとErrorCode Enumを定義する
    • 固有ExceptionHandlerは @RestControllerAdvice(basePackages = "...") でスコープを限定する

    5.3 例外ハンドラー規則

    • GlobalExceptionHandler（common）で共通例外を一括処理する
    • ログ出力にはEnumで定義したメッセージテンプレートを使用し、ハードコードしない
    • エラーレスポンスは ErrorResponse(code, message) 形式で統一する

    6. レスポンスDTO

    • クラスレベルに @JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class) を付与する
    • null項目を省略する場合は @JsonInclude(JsonInclude.Include.NON_NULL) を付与する
    • ネストしたDTOはレスポンスクラス内にstatic inner classとして定義する

    7. ログ出力

    レベル 用途
    warn バリデーションエラー、データ未存在、在庫不足等のクライアント起因エラー
    error サーバー内部エラー、想定外例外
    • ログメッセージはEnumクラスに定義し、SLF4Jプレースホルダ {} を使用する

    8. DynamoDB層（dynamodbモジュール）

    • Entityクラスに @DynamoDbBean を付与する
    • PKには @DynamoDbPartitionKey、SKには @DynamoDbSortKey を付与する
    • カラムマッピングは @DynamoDbAttribute("snake_case_name") で明示する
    • Repositoryは AbstractDynamoDbRepository<T> を継承する
    • ページネーション結果は PagedResult<T> で返す

    9. テスト

    • テストクラスは src/test/java 配下にプロダクションコードと同一パッケージで配置する
    • DIが不要なクラス（Facade, Service等）は @SpringBootTest を使わず、Mockito単体テストで記述する
    • @SpringBootTest はDIコンテナやサーバー起動が必要な結合テスト（Controller層、SecurityFilter等）にのみ使用する

    9.1 DIが不要な場合（Facade / Service）

    // ✓ OK: Mockitoのみで依存を差し替える（高速・軽量）
@ExtendWith(MockitoExtension.class)
class ProductFacadeTest {

    @Mock
    private ProductService productService;

    @InjectMocks
    private ProductFacade productFacade;

    @Test
    void getProduct_正常取得() {
        Product product = new Product();
        product.setProductId(1L);
        product.setProductName("テスト商品");

        when(productService.getProductById(1L)).thenReturn(Optional.of(product));

        ProductResponse response = productFacade.getProduct(1L);

        assertThat(response.getProductId()).isEqualTo(1L);
    }
}

    9.2 DIが不要な場合（Controller）

    Controllerテストも MockMvcBuilders.standaloneSetup() を使用し、@SpringBootTest を使わない。 ExceptionHandlerの検証が必要な場合は setControllerAdvice() で登録する。

    // ✓ OK: standaloneSetupでDIコンテナを起動せずテストする
@ExtendWith(SpringExtension.class)
class ProductControllerTest {

    private MockMvc mockMvc;

    @Mock
    private ProductFacade productFacade;

    @InjectMocks
    private ProductController productController;

    @BeforeEach
    void setUp() {
        mockMvc = MockMvcBuilders.standaloneSetup(productController)
                .setControllerAdvice(new GlobalExceptionHandler())
                .build();
    }

    @Test
    void 商品詳細取得_正常系() throws Exception {
        when(productFacade.getProduct(1L))
                .thenReturn(ProductResponse.builder().productId(1L).build());

        mockMvc.perform(get("/api/v1/products/1"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.product_id").value(1));
    }
}

    9.3 @SpringBootTest を使用するケース

    SecurityFilterや複数Bean連携など、DIコンテナの起動が不可欠な結合テストにのみ使用する。

    9.4 判断基準

    テスト対象 方式 理由
    Facade @ExtendWith(MockitoExtension.class) + @InjectMocks 依存はServiceのみ、DIコンテナ不要
    Service @ExtendWith(MockitoExtension.class) + @InjectMocks 依存はRepositoryのみ、DIコンテナ不要
    Controller @ExtendWith(SpringExtension.class) + standaloneSetup MockMvcでHTTP検証可能、DIコンテナ不要
    Security統合 @SpringBootTest + @AutoConfigureMockMvc Filterチェーンの検証にDIが必要

    10. ビルド・設定ファイル

    • ビルドツール: Gradle (Groovy DSL)
    • Java: 17
    • 共通依存はルート build.gradle の subprojects ブロックで定義する
    • プロファイル設定ファイル: application-{profile}.yaml

    11. その他

    • コメントはJavadocスタイルでクラスおよびpublicメソッドに付与する
    • wildcard import (*) は使用しない（java.util.* 等の標準ライブラリの一部は許容）
